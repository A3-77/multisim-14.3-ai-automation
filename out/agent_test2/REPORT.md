> 测试者：外部使用者 Agent（只读 MCP `tools/list`，不知道 Multisim 任何内部概念）

> 约束：全程只走 MCP 协议，未 import 项目模块、未调 `msbuild`、未构造 Circuit IR、未碰 `.ms14`

## 任务（这次没给任何设计思路，只给指标）

> 设计一个 1kHz 正弦输入经过二阶低通滤波器，截止频率约 2kHz，
> 要求输出幅值和理论值进行验证。

---

## 我的设计决策

二阶 RC 梯形低通，两节取相同值（`R1=R2=R`、`C1=C2=C`），传函：

```
H(s) = 1 / (1 + 3·sRC + (sRC)²)
fc   = 1 / (2πRC) = 2 kHz   ->   RC = 79.6 µs
```

取 E12 标准值：

| | 值 | fc |
| --- | --- | --- |
| R | 10 kΩ | |
| C | 8.2 nF | **1940.9 Hz**（目标 2 kHz，−3.0%，设计选择） |

1 kHz 处理论值：`|H| = 0.58434`、`∠H = −64.58°`、`Vout = 0.58434 V`。

## 结果：**电路建成了，仿真被拒**

### 1. 建电路：16 次调用，零错误

| 步骤 | 调用 | 结果 |
| --- | --- | --- |
| 1–2 | `initialize` / `tools/list` | 8 个工具都在，含新增的 `get_circuit` |
| 3 | `create_circuit` | `c-...` |
| 4–9 | `add_component` × 6 | V1 / R1 / C1 / R2 / C2 / GND1 |
| 10–13 | `connect` × 4 | 见下面拓扑 |
| 14–15 | `add_probe` × 2 | P1→`in`、P2→`n2` |
| 16 | `get_circuit` | 6 元件 / 4 网络 / 2 探针，`warnings: []` |
| **17** | **`simulate`** | **`LAYOUT_UNSUPPORTED`** |

`get_circuit` 读回来的拓扑完全正确：

```
in  ['V1.1', 'R1.1']
n1  ['R1.2', 'C1.1', 'R2.1']        <- 三引脚节点（分流支路）
n2  ['R2.2', 'C2.1']                <- 输出
0   ['C1.2', 'C2.2', 'V1.2', 'GND1.1']
```

**这是一张教科书式的二阶 RC 梯形网络**，`warnings` 是空的 —— 电路本身没有任何问题。

### 2. 仿真被拒，错误信息很清楚

```json
{
  "code": "LAYOUT_UNSUPPORTED",
  "message": "网络 'n1' 有 2 个分支（C1.1, R2.1）",
  "hint": "第一版只支持串联链；并联 / 多支路的布局还没验证过。",
  "context": {"net": "n1", "branches": ["C1.1", "R2.1"]}
}
```

它准确指出了**哪条网络、哪个引脚分叉**。我没有猜、没有重试十次 ——
一看就知道这不是我连错了，是后端不支持这种拓扑。

---

## 这次测试真正证明了什么

**必须把两件事分开看：**

| 层 | 结论 | 证据 |
| --- | --- | --- |
| **MCP 语义层（API）** | ✅ **够用** | 6 个元件、4 条网络（含三引脚节点和四引脚地网）、2 个探针，全部用语义参数建出来，16 次调用零错误，`warnings: []` |
| **后端布局层（P2）** | ❌ **挡住** | `plan_layout()` 只认单链、`MAX_PASSIVES = 2` |

也就是说：**API 已经能表达二阶电路了，只是后端还画不出它的坐标。**

这和第一次验收的结论拼在一起才有意义：

- 第一次（一阶 RC）：API 够用 + 后端够用 → 端到端通过，误差 −0.577%
- 第二次（二阶 RC）：**API 够用** + 后端不够用 → 卡在布局

所以"MCP semantic layer 是否成立"这个问题，答案要分两半：

> **表达层成立了**（Agent 能把多节点电路准确描述出来，一次就对）；
> **执行层还没跟上**（布局只覆盖单链）。

---

## v0.6.2 的修整在这次测试里的实际效果

| v0.6.1 的问题 | 这次的表现 |
| --- | --- |
| `params` 泄漏参数序号 | 我全程用 `parameters={"frequency": 1000}`，一次就对 |
| `measure` / `get_waveform` 的通道键不一致 | 没机会测（没跑成仿真），但 `probe_id` 在 `add_probe` / `get_circuit` 里是一致的 |
| 没有 `get_circuit` | **直接受益**：第 16 步用它确认了"电路建对了、只是跑不了"，否则我只能猜是自己连错了还是后端不支持 |
| 错误 `context` 结构不统一 | `LAYOUT_UNSUPPORTED` 的 `context` 是 `{net, branches}`，干净 |

第 16 步 `get_circuit` 是这次最有价值的一步：**它把"我的电路对不对"和"后端能不能跑"分开了。**
没有它，`LAYOUT_UNSUPPORTED` 会让我怀疑自己。

---

## 结论与下一步

1. **v0.6.2 的 API 修整有效**，但还没被完整验证 —— 因为二阶电路没跑到 `measure` / `get_waveform`。
2. **真正的下一块是 P2（并联 / 多支路布局）**，不是 LLM。这不是猜的，是这次 `simulate` 直接拒出来的。
3. P2 做完之后，用**完全相同的这个脚本**再跑一次（`out/agent_test2/run_task2.py` 不用改），
   就能拿到二阶电路的实测值 vs 理论值 —— 那才是"MCP semantic layer 成立"的完整证据。

### 顺带一个体验问题（不是缺陷）

`connect` 阶段完全没有任何"这个拓扑以后排不了版"的预警，电路能建完 6 个元件，
到 `simulate` 才被拒。对 Agent 来说，如果能更早提示，就能更早改方案。
不过反过来说：**建得出来、跑不了**比**建都建不出来**好 —— 至少 `get_circuit` 能让我看到自己描述对了。
