## 0. 结论先行

**元件库恢复了，但它对 Agent 的能力没有直接增益。**

Agent 加不了二极管，**不是因为元件库坏了**，而是因为项目自己设了两道闸：

1. `tools/circuit_ir.py` 的 `PART_SPECS` 只登记了 **5 种两端元件**，其余一律 `UNKNOWN_COMPONENT_TYPE`；
2. `tools/layout.py` 只做 **两端口串联/并联** 的坐标规划，三端/五端器件没有位置。

而 `msbuild.py` 那一层（donor 克隆 + 连线 + 探针 + 真机仿真）**本来就是好的** —— 实测用二极管、NPN 都跑出了正确的电气结果。

| 判断 | 结果 |
|---|---|
| 升级破坏原有功能？ | **没有**。一阶 RC 复测 gain 差 **0.003%** |
| donor 池有多大？ | corpus 32 种 + 官方样例 161 种 = **193 种** |
| 二极管/NPN/运放 有没有 donor？ | **全都有**（不是缺失） |
| 能不能提取成可复用模板？ | **能**，引脚名 + SPICE 模板全可读 |
| 能不能重建并真跑仿真？ | 二极管 ✅ / NPN ✅ / 运放 ⚠️ |
| COM 能枚举/搜索/放置元件吗？ | **不能**，一个接口都没有 |
| 元件库值不值得整合？ | **值得，但不是你想的那个用法**（见 §4） |

## 2. 原有能力复测（一阶 RC 低通）

### 2.1 方法

复测脚本：`tools/_rerun_rc.py`，产物在 `out/agent_v083/p1/`。

### 2.2 调用序列（14 次，0 错误）

```

create_circuit        -> c-40c641a498
add_component ×4      -> V1(AC 1V/1kHz) R1(1k) C1(330nF) GND1

add_probe ×2          -> 故意先加 P_out 再加 P_in（验 v0.8 的配对修复）
```

### 2.3 与 v0.8.0 基线逐项对账

| 项 | v0.8.0（14.3.0） | 本次（14.3.3） | 差异 |

## 4. 两条路径的实测比较

### 路径 A：继续用 donor（现状）

**可行性：已验证。** 二极管、NPN 都在 msbuild 层跑出了正确的电气结果。

**要补的东西（按工作量排序）**：

| 改动 | 位置 | 工作量 | 风险 |
|---|---|---|---|
| 扩 `PART_SPECS`：加引脚名 + 别名 | `circuit_ir.py` | 小。**引脚名能从 donor 自动读出**，可以写个生成器 | 低 |
| 扩 `layout.py`：三端器件的坐标模板 | `layout.py` | **大**。每类拓扑（共射/分压偏置/跟随器/整流）都要单独设计 | **高**，是真正的工作量 |
| 参数映射：`value` → 正确的参数槽 | `circuit_ir.py` | 中。二极管/NPN 的参数槽是 0 个（型号决定一切），R/C 才是 1 个主参数 | 中 |

**优点**：链路已验证；不依赖 Multisim 数据库（Agent 运行时零依赖）；离线可测。
**缺点**：受 donor 覆盖限制 —— 但现在覆盖率是 **193 种**，比想象的大得多。

### 路径 B：从元件库生成模板，建 Component Template Registry

**可行性：取决于怎么取模板。**

| 取法 | 实测结果 |
|---|---|
| **COM 接口** | ❌ **不可行**（见 §5） |
| **GUI 自动化**（Ctrl+W 搜索 → 放置 → 保存） | ⚠️ 可行但脆弱。需要窗口枚举 + 输入 + 保存，任何 UI 改动都会断；且 14.3.0 时代实测过 Ctrl+W 在焦点不对时根本不触发 |
| **直接用官方样例目录** | ✅ **已经在用**，而且不需要写任何新代码 |

**这是这次调查最重要的发现**：

> **路径 B 想解决的问题（"从库里拿到更多元件"），官方样例目录已经解决了 —— 118 个 .ms14 覆盖 193 种元件，而且是 NI 自己画的、结构最规范的样例。**

也就是说：

- **不需要**为了"扩充元件种类"去做 GUI 自动化或 COM 库访问；
- **需要**做的是把 `PART_SPECS` 从 5 种扩到几十种，并把 `layout.py` 扩到支持三端器件。

### 路径 A vs B 结论

| 维度 | A（donor） | B（库→Registry） |
|---|---|---|
| 现在能不能用 | ✅ 已验证 | ❌ COM 走不通 |
| 元件覆盖 | 193 种（够用） | 理论上全库，但取不出来 |
| 新增工作量 | 主要花在 `layout.py` | 主要花在 GUI 自动化，且不稳定 |
| Agent 运行时依赖 | 零（纯文件） | 零（如果模板落地成文件） |
| 风险 | 拓扑模板设计 | UI 变动、DB 再次损坏 |
| **建议** | **走 A，把 B 的"模板仓库"概念借过来** | — |

**推荐做法（A+B 混合，但不碰 COM/GUI）**：

1. 写一个**离线**的 `tools/build_registry.py`：扫 `corpus/samples14` + 官方样例，对每个 (family, part) 输出一份模板元数据（引脚名、引脚相对坐标、SPICE 模板、参数槽索引、图形对象数）；
2. 产物落到 `registry/components.json`，纳入版本管理；
3. `circuit_ir.py` 的 `PART_SPECS` 从这份 JSON 读，而不是硬编码 5 条；
4. `layout.py` 按器件引脚数分派不同的坐标模板（2 端走现有逻辑，3 端新增共射/跟随器模板）。

**这个方案完全不需要 Multisim 数据库在线**，只是把"元件库恢复"这件事的价值兑现成了"一次性的离线扫描"。

## 5. COM 与数据库接口调查（14.3.3 实测）

### 5.1 COM 到底暴露了什么

`MultisimApp` 对象，**总共 16 个成员**：

```
AddRef  Connect  Disconnect  GetIDsOfNames  GetTypeInfo  GetTypeInfoCount
Invoke  IsConnected  LastErrorMessage  LogFile  NewFile  OpenFile
Path  QueryInterface  Release  VersionInfo
```

**没有一个跟元件库有关。** 没有 `EnumLibraries`、没有 `SearchComponent`、没有 `PlaceComponent`。

`Circuit` 对象，**46 个成员**，与库相关的只有：

```
EnumComponents    EnumSections    EnumVariants
EnumInputs        EnumOutputs     EnumCircuitParameters
ReplaceComponent  CreateSnippet   SaveDesignAsSnippet
```

其中 `EnumComponents/EnumSections/EnumInputs/EnumOutputs` 全是**当前电路内**的对象，不是元件库。

### 5.2 `ReplaceComponent` —— 唯一的库入口，但不可用

先说 `msc.py` 本身：它有 40 多个方法（`components` / `sections` / `rlc` / `params` / `variants` / `probes` / `run` / `transient` / `ac_sweep` / `dc_op` / `netlist` / `bom` / `save_as` …），
**唯一一个参数里带 `source_database / source_group / source_family / source_name` 的就是 `replace_component`（第 220 行）**，
而且它**在产品代码里零调用方** —— 全仓库只有本轮两个探查脚本（`_probe_com.py`、`_probe_replace.py`）试过，从 v0.1 到现在从来没被跑通过。

签名（`msc.py:220`，**参数类型写错了**）：

```python
def replace_component(self, comp, section, source_database, source_group,
                      source_family, source_name, model_name=""):
```

实测：

| 传参 | 结果 |
|---|---|
| `source_database="Master Database"` | `invalid literal for int() with base 10: 'Master Database'` → **第 3 个参数要 int，不是字符串** |
| `source_database=0, group="Diodes", family="DIODE", name="1N4148"` | **Multisim 进程直接崩溃**（进程消失，无异常抛出） |

**结论：`ReplaceComponent` 在 14.3.3 上不可用，而且会带走整个 Multisim 进程。`msc.py` 的这个封装从来没被真正跑通过**（v0.8 的 grep 结论也一致：全项目零调用方）。

### 5.3 COM 不支持，GUI 自动化行不行？

技术上可行（枚举窗口 → 发按键 → 保存），但：

- 14.3.0 时代实测：`Ctrl+W` 在焦点不在原理图时**完全不触发**（我这次复现过）；
- 元件选择对话框是模态的，搜索要输中文/英文型号，还要选 group/family；
- 每次放完要 `SaveAs`，再解析 `.ms14`；
- **任何 UI 微调都会断，而且没有错误码，只有"没反应"。**

对比之下，官方样例目录是**静态文件**，扫描一次 118 个文件只要十几秒，结果是确定的。**没有理由选 GUI 自动化。**

### 5.4 有没有可靠的批量提取方案？

**有，而且已经在仓库里了**：

```
tools/msmodel.py  Circuit.load()     读 .ms14（DCL 解压 + 无损 XML 解析）
                  .components()      列元件（family/part/ciid）
                  .pin_info(ciid)    引脚名 + 绝对坐标
                  .params(comp)      参数槽
tools/msbuild.py  find_part()        按 (family, part) 找 donor，自带官方样例兜底
                  load_donor()       带缓存
```

`tools/_scan_ext.py` 已经能一次扫完 193 种元件。把它扩成正式的 `build_registry.py` 就是 §4 的推荐方案。

## 8. 怎么复现（全部命令都在项目根执行）

**前置**：Multisim 必须是 14.3.3，且没有残留进程。

```bat
taskkill /F /IM multisim.exe
```

所有脚本都要用 **32 位运行时**（`win32com` 只有 32 位版能连 Multisim）：

```bat
set PY=runtime\py32\python.exe
```

| 想验证什么 | 命令 | 预期 |
|---|---|---|
| 原有功能没坏 | `%PY% tools\_rerun_rc.py` | 14 次调用 0 错误，`gain≈0.4333`，约 25 s |
| 和 v0.8 逐项对账 | `%PY% tools\_compare.py` | 打印差值表，gain 差 < 0.01% |
| donor 池有多大 | `%PY% tools\_scan_pool.py` → `%PY% tools\_scan_ext.py` | 32 → **193** |
| 元件结构能不能提出来 | `%PY% tools\_probe_parts.py` | 11 种元件的引脚名 + SPICE 模板 |
| 二极管能不能真跑 | `%PY% tools\_probe_diode.py` | MCP 报 `UNKNOWN_COMPONENT_TYPE`；绕过后 `max=4.3751` |
| 三端器件能不能真跑 | `%PY% tools\_probe_3pin.py` | NPN `Vbe=0.6666`；**运放 `outputs=[]`** |
| COM 有没有库接口 | `%PY% tools\_probe_com.py` | 16 / 46 个成员，零库接口 |
| `ReplaceComponent` 可用吗 | `%PY% tools\_probe_replace.py` | **会让 Multisim 崩溃**，跑之前先存好别的东西 |
